# 历史列表计划

本文是 `docs/演进计划.md` 的模块 D 的执行计划：提交行上的**同步标记**。
起因是对照一个更完整的桌面客户端的历史快照——它除 ahead/behind 外还把三组 hash 交给行视图。

现状一句话：我们已经算了 ahead/behind 两个数字，但只在侧栏和工具栏显示；提交行上看不出哪条没推送。

## 一、现状

| 事实 | 位置 |
| :--- | :--- |
| 已经跑 `git rev-list --left-right --count HEAD...@{upstream}`，只取两个数字 | `sync.go:18` / `sync.go:32` |
| 结果进 `repoMeta.ahead` / `behind`，随 `loadMeta` 一起取 | `git.go:638` |
| 只显示在侧栏仓库行与工具栏 | `main.go:758` / `main.go:492`（`syncBadge`） |
| 提交行 `subject` 列：refs 徽章 + provenance 徽章，没有同步位 | `main.go:1253`（`commitCell`） |
| 现有图标可直接用：`iconUpload`（↑）、`iconDownload`（↓） | `icons.go:120` 附近 |

## 二、抄什么，不抄什么

### 抄

| 项 | 做到什么程度 |
| :--- | :--- |
| 行级「待推送」 | 未推送的提交行显示 ↑ 图标徽章，颜色 `Accent`，tooltip `待推送` |
| 行级「远端独有」 | 上游独有、本地没有的提交行显示 ↓ 图标徽章，颜色 `TextMuted`，tooltip `远端独有` |

顺手改掉一处浪费：把 `--count` 去掉，一次进程同时拿到两组 hash 与数量。

### 不抄

| 项 | 为什么不做 |
| :--- | :--- |
| 不可达 HEAD 的行降饱和 | 要额外的 `git rev-list <tips> --not HEAD`，等于每次 reload 多走一遍全量历史，和 `docs/performance-memory-review-2026-11-02.md` 的口径冲突 |
| 「定位到第一条 incoming」 | 留候选，见 §四。它要一直 `loadMore` 到那条提交出现，和分页、预算都要重新对齐 |
| 行内显示 ahead/behind 数字 | 侧栏已经有；一行只放一个类型徽章（`docs/界面文案规范.md`） |
| 按同步状态过滤/排序 | 现在没有过滤模型，先不引入 |

## 三、第 1 步：行级同步徽章

**可见结果**：仓库配了 upstream 时，未推送的提交行显示 ↑，远端独有的提交行显示 ↓；
没配 upstream 时两个徽章都不出现。

**改动**

1. `cmd/gitclient/sync.go`

   ```go
   type syncStatus struct {
       upstream           string
       hasUpstream        bool
       ahead, behind      int
       incoming, outgoing [][20]byte // 远端独有 / 本地独有
   }
   ```

   `queryTrackingStatus` 把 `rev-list --left-right --count` 换成不带 `--count` 的同一谓词，
   逐行读：`<hash` 进 `outgoing`，`>hash` 进 `incoming`；`ahead = len(outgoing)`、`behind = len(incoming)`。
   一次进程、一次遍历，没有额外开销。

2. `cmd/gitclient/git.go`：`repoMeta` 收 `[][20]byte`，`loadMeta` 转成
   `repoTab.incoming, outgoing map[[20]byte]bool`——切片是取数格式，map 是行渲染的查表格式，
   两者在 `loadMeta` 交界处转换一次，别在 `commitCell` 里线性找。

3. `cmd/gitclient/repo.go`：`installHistory`（`repo.go:529`）落到 `repoTab.incoming` / `outgoing`。

4. `cmd/gitclient/main.go`：`commitCell` 的 `subject` 列，在 refs 徽章之后、provenance 徽章之前插入。
   新增一个小辅助函数，照 `chipSoft`（`lobe_widgets.go:232`）的形状，但只放图标：

   ```go
   // iconBadge 是只有图标的类型徽章，行里用来标同步状态。
   func iconBadge(c *ui.Context, key string, icon *ui.SVG, color ui.Color, tip string) ui.Element
   ```

   用法：

   ```go
   if tab.outgoing[item.hash] {
       iconBadge(c, "sync-out-"+hashHex(item.hash), iconUpload, t.Accent, tr("待推送"))
   } else if tab.incoming[item.hash] {
       iconBadge(c, "sync-in-"+hashHex(item.hash), iconDownload, t.TextMuted, tr("远端独有"))
   }
   ```

   图标 12px，左右各 2px 内边距，和 provenance 徽章（11px 字号）同一视觉重量。
   `worktree` 行（未提交改动）不显示。

5. `cmd/gitclient/locales/en.json`：`待推送`、`远端独有`。

**不做**：不加计数、不改行高与列宽、不加过滤与排序、不动 `syncBadge` 的文案。

**验收**
- upstream 落后两个提交的仓库：`ahead = 2`，那两行有 ↑，其余行没有。
- 先 fetch 再 `git reset --hard HEAD~1`：远端独有那行有 ↓。
- 没配 upstream：两种徽章都不出现。
- `go test ./cmd/gitclient/ -run 'TestSyncSets'`：`rev-list --left-right` 输出解析（空输出、只有一侧、
  两侧都有、哈希带前缀符号）。

## 四、候选（不排期，触发条件写死）

| 候选 | 触发条件 | 形状 |
| :--- | :--- | :--- |
| 定位到第一条 incoming | 出现「几千条提交里找不到要 pull 的那条」的真实反馈 | 菜单项 + 循环 `loadMore` 直到那条提交出现，途中显示进度 |
| 搜索索引复用 | 大仓库单次搜索超过 1s 成为可复现反馈 | 只存 hash + 匹配文本的紧凑索引；当前页用 `git log --no-walk --stdin` 物化 |
| 不可达 HEAD 降饱和 | 「全部分支」范围下经常被误读成「这些都在当前分支」 | 先解决 `rev-list <tips> --not HEAD` 的代价：只在 reload 且 tip 数 > 1 时跑，结果随 reload 失效 |

## 五、顺序与时间盒

0.5 天，只有一步。

## 六、风险

| 风险 | 处理 |
| :--- | :--- |
| 没有 upstream 时 `rev-list` 失败 | 与现在一致：先 `rev-parse @{upstream}` 探路，失败即返回空集合 |
| 集合占内存 | 只存 hash（`[20]byte`）；纯线性历史下两个集合最多各 `ahead` / `behind` 个元素 |
| 徽章和 refs 徽章在窄列里挤 | 徽章只放图标；窄窗口已有 `mainW < 700` 的列宽分支，`subject` 仍有 `MinWidth` |
| `rev-list --left-right` 输出被 `core.abbrev` 之类影响 | 不用 `--abbrev`，拿完整 hash；解析前 `strings.TrimSpace` + 校验长度 40 |
